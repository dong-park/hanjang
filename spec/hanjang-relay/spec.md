## 문제 — 방은 맥에서만 열리고, 같은 와이파이 안에서만 닿는다

지금 방장은 맥 앱이나 맥의 헤드리스 프로세스뿐이다. 휴대폰 웹은 참가만 한다. 사용자가 "릴레이로 웹에서도 방장을 하고 공개 게임방도 만들자"고 했다.
관련 선행 spec은 spec/hanjang/spec.md와 spec/hanjang-web/spec.md다. 여기서는 hanjang-web의 D2 "휴대폰은 참가만"을 뒤집는다.

## 목표 — 서버가 방을 들고, 폰만 있어도 방을 만들거나 공개 방에 들어간다

미니PC의 서버가 방을 열어 두고, 누구든 브라우저로 방을 만들거나 목록에서 골라 들어간다.
규칙과 연출은 맥 앱과 같다. 방 주인의 폰이 잠겨도 판이 이어지는 것이 구조 선택의 기준이다.

## 비목표 — 계정, 랭킹, 채팅은 하지 않는다

- 계정과 로그인은 하지 않는다. 신원은 기기에 저장한 토큰 하나다.
- 랭킹, 전적 저장, 채팅은 하지 않는다.
- 규칙 변경과 새 연출은 하지 않는다. 규칙은 spec/hanjang이 갖는다.
- 맥 앱 LAN 방장 경로의 제거는 D7이 정한다. 기본은 남긴다.
- 방 상태를 서버 재시작 뒤에 되살리지 않는다.

## 성공 기준 — 행 파일이 곧 성공 기준이다

행 파일이 곧 성공 기준이다.

## 경계 조건 — 서버가 죽거나, 낯선 사람이 오는 경우

- 방 하나는 2~4명이다. 다섯째는 지금 문구와 같이 거절된다.
- 서버가 재시작되면 모든 방이 사라진다. 사람들은 이유를 보고 첫 화면으로 간다.
- 서버에는 닉네임과 방 이름 외의 개인정보를 두지 않는다.
- 폰은 화면이 꺼지면 접속이 끊긴다. 나간 사람과 같이 처리한다.
- 터널을 쓰면 접속이 서버에 도착하는 곳이 로컬 주소로 보인다. 주소별 제한은 터널 앞의 헤더를 본다.

## 상태 모델 — 방은 열림에서 판 중을 거쳐 닫힌다

| 상태 | 합법 전이 |
|---|---|
| 대기 | 판 중, 닫힘 |
| 판 중 | 대기(판 끝), 닫힘 |
| 닫힘 | 없음 |

불가능한 조합: 닫힌 방이 목록에 보임. 판 중인 방에 새 사람이 들어옴. 접속자 0명인 방이 60초 넘게 열려 있음.

## 기술 결정 — D1이 나머지를 가른다

핵심 어려움은 Godot 멀티플레이가 접속자 번호를 프로토콜 안에서 붙인다는 점이다. 서버가 패킷만 나르는 구조(D1 A)는 번호를 흉내 내는 피어를 서버에 만들어야 한다. 추천은 C다. 방마다 헤드리스 Godot를 띄우면 rules.gd와 session.gd를 그대로 쓰고, 방장이 없으니 방장 폰 문제가 없다.
C의 비용은 두 가지다. 방 프로세스가 방장 자리 없이 도는 코드 변경이 필요하다. 방 하나가 프로세스 하나라 동시 방 수가 미니PC 메모리에 묶인다. 이 둘은 n1 프로토타입에서 숫자로 잰다.

## 확인 안 된 것 — 서버와 브라우저 연결 모두 미확인이다

- 사용자가 말한 연결된 미니PC가 dongpark인지. dongpark은 tailscale에서 offline이다.
- 미니PC의 사양, node, python, cloudflared, docker 유무.
- 폰 브라우저가 wss 터널로 Godot 웹소켓에 붙는지(T2가 첫 확인).
- 헤드리스 Godot 한 개가 쓰는 메모리와 시작 시간.
- Godot 웹소켓 서버의 ping 설정이 FIN 없는 끊김을 20초 안에 잡는지.

## DAG — 접근과 프로토타입이 먼저고, 서버 구조는 그 위에 쌓는다

| 웨이브 | 노드 | 비고 |
|---|---|---|
| 1 | n1-proto | 서버 접근 확인과 브라우저 wss 연결 확인. D8이 A면 맥에서 한다 |
| 2 | n2-dedicated, n3-manager | n2는 게임 코드, n3는 별도 서비스. 파일이 겹치지 않는다 |
| 3 | n4-trust, n5-drops | 둘 다 n2 뒤. n4는 n3도 필요 |
| 4 | n6-lobby-ui, n7-deploy | n6는 n3·n4, n7은 n3 |
| 5 | n8-verify | 실제 폰과 미니PC |

```
n1-proto ──┬──► n2-dedicated ──┬──► n4-trust ──┬──► n6-lobby-ui ──┐
           │                   └──► n5-drops   │                  ├──► n8-verify
           └──► n3-manager ────────────────────┴──► n7-deploy ────┘
```

연결 사유

- n2, n3 ← n1: D1이 C인지 프로토타입이 숫자로 확인한 뒤에 쓴다.
- n4 ← n2, n3: 토큰이 방 프로세스와 관리 서비스 양쪽에 있다.
- n5 ← n2: 승계와 ping은 방 프로세스 안에서 돈다.
- n6 ← n3, n4: 목록 API와 토큰이 있어야 화면이 쓴다.
- n7 ← n3: 배포할 서비스가 있어야 한다. D2·D3·T1 결과가 필요하다.
- n8 ← n6, n7, n5: 모든 것이 합쳐진 뒤에만 실폰 시험이 돈다.
